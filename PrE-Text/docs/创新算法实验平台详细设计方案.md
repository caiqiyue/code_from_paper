# 论文实验平台与创新算法总体设计方案

## 1. 文档定位

本文档用于把当前仓库中的已有论文代码、你在 [研究思路.md](D:/学习记录/导师项目/研究/caiqiyue_file/docs/研究思路.md) 中提出的创新算法思路，以及最终需要落地的实验平台，统一整理成一份可执行的总方案。

这份文档要同时解决四件事：

1. 明确你的创新算法到底由哪些阶段组成。
2. 明确每个阶段借用了哪篇论文的哪部分能力。
3. 明确哪些模块有源码可复用，哪些模块必须自研实现。
4. 明确最终实验平台的目录结构、技术框架、配置设计和实施顺序。

本文档默认遵守以下工程边界：

- 不微调服务端大模型。
- 服务端主要通过 Prompt 迭代驱动生成分布演化。
- 客户端仅运行轻量模型或轻量打分逻辑。
- 本地开发环境可以是 Windows，但代码与路径设计必须兼容 Linux 服务器。
- 所有平台路径必须使用相对路径与 `pathlib` 管理，不能把 Windows 绝对路径写死进代码。

## 2. 研究目标与核心问题

你的创新算法不是单篇论文的复现，而是一个跨论文拼接、再重新设计目标函数和联邦交互方式的系统。

目标问题可以概括为：

> 在不微调服务端大模型的前提下，如何让服务端仅依靠多轮 Prompt 迭代，就能持续生成更贴近各客户端 Non-IID 私有分布的高质量合成文本，同时尽量不泄露客户端原始数据。

与现有基线相比，你的方法要解决三个根本问题：

1. `PrE-Text` 的筛选指标过于浅层，容易把“字面接近但逻辑错误”的样本误判为好样本。
2. `PrE-Text` 的客户端反馈带宽太低，只有直方图或相似度统计，服务端不知道具体该怎么改 Prompt。
3. 免微调场景下，如果只靠随机 Prompt 变异，优化方向极不稳定，收敛慢且上限低。

因此，你的方法主线不是“更强的生成器”，而是：

- 用更可靠的 `scorer` 找出真正有害的坏样本。
- 用对比式 `critic` 把坏样本的缺陷翻译成自然语言规则。
- 用更强的 `aggregator` 把多客户端反馈聚合成下一轮 Prompt 更新。

## 3. 创新算法的总体框架

## 3.1 总体闭环

你的主方法可以抽象为如下联邦闭环：

`server prompt -> synthetic generation -> client bad-sample scoring -> real-sample retrieval -> contrastive critique -> privacy redaction/compression -> server aggregation -> prompt update -> next round generation`

对应到平台中的统一阶段为：

`generator -> scorer -> selector -> retriever -> critic -> redactor -> aggregator -> prompt_updater -> evaluator`

## 3.2 与 PrE-Text 的关系

你的方法不是完全抛弃 `PrE-Text`，而是把它降级为“服务端生成基线”。

保留的能力：

- seed 样本生成
- mask-fill 变异
- lookahead + histogram 分布评估
- bootstrap 扩增

被替换或升级的能力：

- 原始余弦相似度 / histogram 筛选被 `DataInf / GRADMM / IRA` 替代或并列对比
- 原始统计反馈被 `FedTextGrad` 风格文本批判替代
- 原始随机 Prompt 进化被 `UID / DBSCAN-Attn / TSGD-M` 风格聚合更新替代

## 3.3 创新算法的三大阶段

### 阶段 A：客户端坏样本诊断

目标是找出真正会损害客户端本地下游效用的合成样本，而不是只找“看起来不像”的样本。

候选方法：

1. `DataInf`
   - 基于 influence function 近似。
   - 关注样本对本地验证损失的因果影响。
2. `GRADMM`
   - 基于梯度匹配与重构损失。
   - 关注合成样本与真实样本在优化轨迹上的偏离。
3. `IRA`
   - 不计算梯度，只用两次前向传播构造低成本指令-响应对齐度分数。
   - 适合作为低算力基线或边缘设备版本。

### 阶段 B：客户端文本化梯度生成

目标是把“为什么这个合成样本不好”转成自然语言 critique，而不是上传一维标量。

基本流程：

1. 从本地召回与坏样本语义最相关的真实样本 `x_real`。
2. 构造 `(x_bad, x_real)` 的对比式提示词。
3. 调用本地轻量 LLM 生成 critique。
4. 做压缩与脱敏。
5. 上传规则级文本反馈而不是原始样本。

### 阶段 C：服务端 Prompt 聚合与更新

目标是把多个客户端的规则级反馈，变成稳定、可执行、可追踪的下一轮 Prompt 更新。

候选方法：

1. `summarization`
   - 直接总结所有 critique。
2. `uid`
   - 基于 FedTextGrad 的 Uniform Information Density 风格聚合。
3. `dbscan_attn`
   - 先聚类 critique，再按簇重要性做聚合。
4. `dbscan_attn_tsgdm`
   - 在 `dbscan_attn` 基础上加入历史动量平滑。

## 3.4 创新点对应关系

| 创新点 | 旧基线问题 | 你的改进 |
| --- | --- | --- |
| 评估机制因果化 | `PrE-Text` 只看相似度或分布贴近度 | 用 `DataInf` / `GRADMM` / `IRA` 评估样本对任务目标的真实效用或对齐度 |
| 反馈信号语义化 | 直方图是低带宽统计，无法指导 Prompt 修改 | 用对比式 critique 直接生成“该怎么改”的自然语言规则 |
| Prompt 更新定向化 | 随机变异收敛慢且不稳定 | 用 `UID / DBSCAN-Attn / TSGD-M` 做有方向、有记忆的文本更新 |

## 4. 算法来源与复用边界

## 4.1 有源码支撑的模块

| 平台模块 | 借用来源 | 复用方式 | 备注 |
| --- | --- | --- | --- |
| `pretext_seed` generator | `PrE-Text` | 抽取变异、lookahead、survivor sampling 核心逻辑 | 不复用原脚本式 DP 实验总流程 |
| `pretext_bootstrap` generator | `PrE-Text` | 抽取 bootstrap 扩增逻辑 | 改为对象接口 |
| `pretext_hist` scorer | `PrE-Text` | 抽取 histogram 支持度评分逻辑 | 需转换成坏样本分数语义 |
| `datainf` scorer | `DataInf` | 抽取逐样本梯度与 influence/HVP 计算 | 只保留 scorer 核心 |
| `gradmm` scorer | `GRADMM` | 抽取梯度匹配、重构损失、perplexity 打分 | 不复用生成和微调脚手架 |
| `fedtextgrad_critic` | `FedTextGrad` | 借用 textual feedback 风格与 prompt 模板思路 | 需重写成对比式 critic |
| `summarization` aggregator | `FedTextGrad` | 借用聚合 prompt 模板思路 | 需要按 critique 输入重写 |
| `uid` aggregator | `FedTextGrad` | 借用 UID 汇总思路 | 原仓库聚合对象是 prompt，不是 critique |

## 4.2 无源码、需要自研实现的模块

| 平台模块 | 来源定位 | 自研原因 | 推荐实现方式 |
| --- | --- | --- | --- |
| `ira` scorer | 来自你计划采用的 IRA 指标思路 | 当前仓库无源码 | 依据公式和任务定义自行实现前向分数器 |
| `dbscan_attn` aggregator | 来自你计划采用的 DBSCAN 聚类聚合思路 | 当前仓库无源码 | `embedding -> DBSCAN -> cluster weighting -> LLM summarize` |
| `dbscan_attn_tsgdm` aggregator | 来自你计划采用的 TSGD-M 动量思路 | 当前仓库无源码 | 在 `dbscan_attn` 上叠加历史更新记忆 |
| `rule_compressor` | 论文平台新增 | 原仓库无现成实现 | 客户端本地或服务端规则压缩器 |
| `redactor` | 论文平台新增 | 原仓库无现成实现 | NER + 正则脱敏 |

## 4.3 关键边界结论

必须明确以下三点：

1. `DataInf` 和 `GRADMM` 在平台中只扮演 `scorer`，不应该连带整个原实验脚手架一起搬进来。
2. `FedTextGrad` 在平台中只提供 `critic` 风格和 `aggregator` 思路，不应整体接管训练流程。
3. `IRA`、`DBSCAN-Attn`、`TSGD-M` 在你当前仓库中没有可直接复用的源码，必须在平台内作为原生新模块实现。

## 5. 平台总体技术架构

## 5.1 分层架构

建议将实验平台拆成七层：

1. `config layer`
   - 管理所有路径、模型、数据、算法参数和实验组合。
2. `data layer`
   - 负责数据下载、预处理、统一 schema、联邦切分与缓存。
3. `model layer`
   - 管理 embedding 模型、本地轻量 LLM、服务端聚合 LLM、外部 API 封装。
4. `algorithm layer`
   - 实现各类算法内核，如 `DataInfCore`、`GradMMCore`、`IRACore`、`DBSCANAttentionCore`、`TSGDMemoryCore`。
5. `adapter layer`
   - 将算法内核封装成统一的 `generator/scorer/retriever/critic/aggregator` 接口。
6. `runtime layer`
   - 负责联邦轮次调度、客户端模拟、日志、异常恢复和中间结果落盘。
7. `evaluation layer`
   - 负责效果指标、系统指标、隐私指标和案例分析输出。


## 6.3 核心上下文对象

建议平台定义四类 context：

1. `RoundContext`
   - 当前轮次、当前 prompt、生成参数、全局随机种子。
2. `ClientContext`

3. `ServerContext`
   - 聚合模型、历史 prompt、聚合记忆状态、全局配置。
4. `EvalContext`
   - 评估集、评价指标、输出路径。

## 7. 创新算法的技术实现方案

## 7.1 Generator 实现

### `pretext_generator`

目标：

- 作为服务端合成数据生成基线。
- 保留 `PrE-Text` 的变异、lookahead 与 survivor sampling 思想。
- 不保留其完整 DP 脚本式流程。

推荐一轮执行流程：

1. 从 `init_population_path` 或上一轮生成样本中抽取父代。
2. 调用 `pretext_variation.py` 生成若干候选变体。
3. 调用 `pretext_histogram` 或内部质量函数估计候选质量。
4. 保留 top surviving candidates。
5. 输出当前轮的 synthetic samples。

### `pretext_bootstrap`

目标：

- 在生成器主流程稳定后，把 seed 样本扩展为更大的 synthetic dataset。

实现要求：

- 直接接收 `seed_samples` 对象列表，而不是依赖文件协议。
- bootstrap 提示模板、每轮扩增数、温度、`top_p`、`max_tokens` 全部配置化。

## 7.2 Scorer 实现

### `datainf`

核心思想：

- 用逐样本梯度与近似逆 Hessian 向量积估计 influence。
- 直接衡量训练样本对本地验证损失的影响。

平台中的统一坏样本语义：

`score = influence_on_local_val_loss`

即：

- 分数越大，代表该合成样本越有害。
- `score_direction = larger_is_worse`

首版建议保留：

- `proposed` HVP 近似
- `target_module in {lora_only, lora_or_last_layer}`
- 逐样本 train gradient
- 逐样本 validation gradient

暂不作为首版默认：

- `accurate` HVP
- `LiSSA`
- diffusion path

### `gradmm`

核心思想：

- 计算候选样本梯度与参考真实样本平均梯度的偏差。
- 结合重构损失与 perplexity 形成坏样本得分。

推荐平台分数：

`badness = rec_loss_ids + alpha * perplexity`

要求：

- 支持 `last_layer / lora / lora_or_last_layer`
- 支持 instruction-response 与分类任务两种格式映射
- 保存中间分量用于可解释性分析

### `ira`

定位：

- 低成本 scorer。
- 适合与 `DataInf`、`GRADMM` 做算力-性能对比。

推荐平台实现思路：

1. 对 instruction-response 样本，计算回答在有条件与无条件下的 token-level loss。
2. 定义：
   - `ira_raw = L(answer) - L(answer | instruction)`
3. 为了统一坏样本语义，建议使用：
   - `badness = -ira_raw`
   - 或更稳妥地做归一化后输出 `larger_is_worse`

实现注意：

- `IRA` 不依赖真实样本梯度。
- 只需要本地轻量语言模型做前向传播。
- 必须做长度归一化，避免长回答天然吃亏。

## 7.3 Retriever 实现

### `knn_retriever`

目标：

- 为每个坏样本召回本地最相关的真实样本 `x_real`。

推荐实现：

1. 用轻量 embedding 模型编码真实样本库与坏样本 query。
2. 对 query 做 KNN 检索。
3. 返回 top-k 真实样本。

### `label_match`

适用场景：

- 分类或显式标签任务。
- 可先按标签过滤，再在标签内做语义检索。

## 7.4 Critic 实现

### `fedtextgrad_critic`

定位：

- 借鉴 `FedTextGrad` 的 textual feedback 思想。
- 但必须从“回答-评测”链改造为“坏样本-真实样本对比”链。

推荐输入：

- `x_bad`
- `x_real`
- 当前 prompt
- 数据集域信息
- 输出规则数量上限

推荐输出：

```yaml
critique_id: str
client_id: str
sample_pair_id: str
rules:
  - rule: str
    severity: float
meta:
  model_name: str
  redacted: bool
```

实现要求：

1. 约束 critic “只给修改建议，不直接重写最终答案”。
2. 优先输出规则级句子，而不是冗长段落。
3. 支持客户端本地压缩为 `n` 条核心规则。
4. 支持 NER 脱敏与正则脱敏。

## 7.5 Aggregator 实现

### `summarization`

最简单的 LLM 聚合基线：

1. 收集所有 critique。
2. 截断到 token 上限。
3. 调用聚合模型输出规则摘要。

### `uid`

定位：

- 作为 `FedTextGrad` 风格聚合基线。

平台改造点：

- 聚合输入是 critique 规则，而不是系统 prompt。
- 输出不是新 prompt 全文，而是 `PromptUpdate`。

### `dbscan_attn`

这是你后续平台里的核心新增聚合器之一。

建议执行流程：

1. 对所有 critique 规则编码成 embedding。
2. 使用 `DBSCAN` 聚类。
3. 丢弃离群噪声或单点极端噪声。
4. 对每个簇计算簇权重。
5. 为每个簇选代表规则。
6. 把“簇代表 + 簇权重 + 簇规模”输入聚合 LLM。
7. 输出结构化 `PromptUpdate`。

推荐簇权重：

`cluster_weight = cluster_size * mean_severity * quality_factor`

这比简单 UID 更适合同质反馈强、共性错误明显的场景。

### `dbscan_attn_tsgdm`

这是最终主方法候选聚合器。

在 `dbscan_attn` 基础上增加历史记忆：

1. 保存前几轮的 `PromptUpdate`。
2. 为当前更新计算语义方向向量。
3. 与历史更新做 EMA 融合。
4. 再将融合结果喂给 prompt updater 生成下一轮 prompt。

推荐动量形式：

`m_t = beta * m_{t-1} + (1 - beta) * u_t`

其中：

- `u_t` 是当前轮聚合更新表示
- `m_t` 是历史动量表示
- `beta` 是记忆强度

## 7.6 Prompt Updater 实现

建议单独设一个 `prompt_updater.py`，不要让聚合器直接改全文 prompt。

统一输出结构：

```yaml
prompt_update_id: str
round_id: int
update_rules:
  - str
summary: str
confidence: float
source_clusters: list[int]
```

更新器职责：

1. 将 `PromptUpdate` 合并进当前 system prompt。
2. 控制最大长度，避免 prompt 持续膨胀。
3. 保留 prompt 历史版本，方便回滚与案例分析。

## 7.7 隐私与安全模块

建议平台显式加入 `redactor` 和 `privacy metrics`。

客户端侧最低要求：

1. NER 脱敏
2. 正则脱敏
3. critique 压缩
4. 不上传真实原文

服务端侧最低要求：

1. 不落盘未脱敏原始 critique
2. 聚合前做安全日志审计
3. 输出时区分“客户端可见”和“内部调试”字段

## 8. 无源码模块的自研实现方案

## 8.1 IRA 指标计算

由于当前仓库没有 `IRA` 源码，建议将其视为一个平台原生 scorer。

推荐接口：

```python
class IRAScorer(Scorer):
    def score(self, samples, client_ctx) -> list[ScoredSample]:
        ...
```

推荐实现步骤：

1. 解析样本为 `(instruction, response)`。
2. 用本地轻量模型计算：
   - `loss_uncond = L(response)`
   - `loss_cond = L(response | instruction)`
3. 计算：
   - `ira_raw = loss_uncond - loss_cond`
4. 做长度归一化和数值裁剪。
5. 输出统一坏样本分数。

推荐元数据：

```yaml
meta:
  loss_uncond: float
  loss_cond: float
  ira_raw: float
  normalized_by_length: true
```

## 8.2 DBSCAN-Attn 聚合器

建议把之前平台草案中的 `dbscan_uid` 明确升级并统一命名为 `dbscan_attn`，因为这里真正的关键不是“UID 的一个变体”，而是“先聚类、再按簇权重聚合”的策略。

推荐实现步骤：

1. `encode(critiques)` 得到 critique embeddings。
2. `DBSCAN(eps, min_samples)` 聚类。
3. 对每个簇计算：
   - `cluster_size`
   - `mean_severity`
   - `intra_cluster_similarity`
4. 计算 attention-like 簇权重。
5. 每簇保留 1 到 `k` 条代表规则。
6. 将代表规则和权重送入聚合 prompt。
7. 输出 `PromptUpdate`。

推荐元数据：

```yaml
meta:
  cluster_count: int
  noise_count: int
  kept_rule_count: int
  cluster_weights: list[float]
```

## 8.3 TSGD-M 动量模块

建议不要把 `TSGD-M` 做成独立聚合器，而是做成可插拔的历史记忆组件：

```python
class TSGDMemory:
    def update(self, current_update, history_state) -> SmoothedUpdate:
        ...
```

推荐实现步骤：

1. 维护最近 `H` 轮的更新摘要。
2. 对每轮更新做 embedding。
3. 基于 EMA 计算历史方向。
4. 将当前更新与历史方向融合。
5. 若当前更新与历史方向冲突过大，则降低其权重。

这样做的好处：

1. 能兼容 `uid` 与 `dbscan_attn` 两种聚合器。
2. 动量逻辑可单独做消融实验。
3. 不会把聚合器本身实现复杂度拉得过高。

## 10.1 阶段 0：平台连通性

## 10.2 阶段 1：Scorer 筛选

- generator = `pretext_seed`

## 10.3 阶段 2：Retriever 与 Critic 验证

固定：

- generator = `pretext_seed`

1. `none + single-sample critique`

## 10.4 阶段 3：Aggregator 筛选

固定：

- generator = `pretext_seed`
- scorer = 阶段 1 最优

- critic = `fedtextgrad_critic`

对比：

1. `summarization`
2. `uid`

4. `dbscan_attn_tsgdm`

目标：

- 证明聚类聚合优于直接汇总

## 10.6 阶段 5：消融实验

## 13. 工程实现要求

## 13.1 Linux 兼容要求

必须满足以下要求：

1. 路径统一使用 `pathlib.Path`。
2. 配置文件内只写相对路径。
3. shell 脚本以 Bash 为主，Windows 只作为开发环境，不作为最终运行假设。
4. API key、HF cache、模型根目录全部从环境变量注入。
5. 不把 PowerShell 专属命令写进平台主流程。

## 13.2 编码要求

1. 算法内核与平台 I/O 分离。
2. 每个模块都能独立单元测试。
3. 所有中间产物可落盘。
4. 所有实验可由单一配置文件重跑。
5. 所有 prompt 模板单独版本化。

## 13.3 运行要求

建议提供三类入口：

1. `scripts/run_experiment.py`
   - 跑单个实验配置。
2. `scripts/run_matrix.py`
   - 跑一批实验矩阵。
3. `scripts/summarize_results.py`
   - 汇总结果表与消融结果。

## 14. 推荐实施顺序

建议按下面顺序开发，而不是同时铺开所有模块：

1. 先实现 `core + configs + schema + output layout`。
2. 先接 `pretext_seed` generator 与 `pretext_hist` scorer。
3. 再接 `datainf` scorer。
4. 再接 `gradmm` scorer。
5. 然后实现 `knn_retriever`。
6. 然后实现 `fedtextgrad_critic + redactor + compressor`。
7. 先做 `summarization` 和 `uid` 聚合器。
8. 再自研 `ira` scorer。
9. 再自研 `dbscan_attn`。
10. 最后接 `tsgd_memory`，组成 `dbscan_attn_tsgdm`。

这个顺序的原因是：

- 先把“可运行、有源码”的部分接起来，尽快形成最小闭环。
- 再逐步补上“无源码、自研”的创新模块。

## 15. 当前最推荐的论文主方法路线

从目前文档、源码条件和你的研究思路综合判断，最有希望成为论文主线的方法是：

`PrE-Text 风格服务端生成 + DataInf/GRADMM 坏样本筛选 + KNN 真实样本召回 + FedTextGrad 风格对比式 critic + DBSCAN-Attn 聚合 + TSGD-M 历史动量平滑`

更细一点地说：

1. 主生成器：`pretext_seed`
2. 主 scorer：优先在 `DataInf` 与 `GRADMM` 中选一个，`IRA` 作为低算力对照
3. 主 retriever：`knn`
4. 主 critic：`fedtextgrad_critic`
5. 主 aggregator：`dbscan_attn_tsgdm`

## 16. 最终结论

这份平台方案最终明确了三件最关键的事：

1. 你的创新算法不是单模块改进，而是“生成-筛选-对比批判-聚合更新”的联邦闭环系统。
2. 当前仓库中真正有源码基础的核心来源是 `PrE-Text`、`DataInf`、`GRADMM`、`FedTextGrad` 四部分；`IRA`、`DBSCAN-Attn`、`TSGD-M` 需要作为平台原生模块自研。
3. 平台落地时必须围绕统一接口、相对路径、Linux 兼容、模块可替换、中间产物可保存这五个原则来实现。

因此，后续开发的正确方向不是“继续堆论文仓库”，而是：

> 以 `thesis_platform/` 为统一主框架，把已有论文代码抽成稳定可替换的模块，再把无源码的创新部分做成平台原生实现。
