# thesis_platform 算法流程静态复核与数值验证报告

日期: 2026-03-14

## 1. 复核目标

本报告用于回答两个问题:

1. 当前 `thesis_platform` 中的实验平台主链是否已经完整实现 `研究思路--第二版.md` 中设计的创新算法流程。
2. 当前平台在真实运行时的数值行为，是否支持前述静态代码复核结论。

本次结论基于两部分证据:

- 静态代码复核: 对 `core/`, `adapters/`, `algorithms/`, `data/`, `evaluation/` 以及实验配置进行逐项对照。
- 数值验证: 运行一组新的 A/B 对照实验，只改变 `generator.initial_prompt`，其余配置保持完全一致，观察生成、打分、检索、critique、聚合结果是否发生变化。

## 2. 静态代码复核结论

结论先行:

> 当前平台已经具备可跑通的 MVP 编排骨架，但还没有完整实现 `研究思路--第二版.md` 中设计的全部创新算法内容。

### 2.1 已经具备的部分

- 已有完整的实验编排主链: `ExperimentRunner -> RoundRunner -> generator -> scorer -> retriever -> critic -> aggregator`。
- 已支持按轮次持久化输出: `generated_samples.jsonl`, `scored_samples.jsonl`, `selected_bad_samples.jsonl`, `retrieved_pairs.jsonl`, `client_critiques.jsonl`, `prompt_update.json`, `round_metrics.json`。
- 已经可以在工程层面完成“生成 -> 客户端评估 -> 本地检索 -> critique -> 服务端聚合 -> prompt 更新”的一轮闭环。

### 2.2 主要缺口

#### 缺口 1: Prompt 更新没有真正驱动下一轮生成

- `core/round_runner.py` 会在聚合后更新 `updated_prompt`。
- `core/experiment_runner.py` 也会把 `updated_prompt` 送回 `server_ctx.prompt_text`。
- 但 `adapters/generators/pretext_generator.py` 生成文本时没有使用 `round_ctx.prompt_text` 参与任何生成逻辑。
- `algorithms/generators/pretext_variation.py` 的实际生成行为只是对 seed text 做随机删词和窗口裁剪。
- 因此，当前实现中 prompt 更像“被记录在元数据里”，而不是“驱动生成分布变化的控制变量”。

这与研究思路中的核心闭环不一致。你的设计要求服务端根据聚合后的文本梯度构造新 prompt，并由新 prompt 直接生成下一轮数据；当前实现没有真正做到这一点。

#### 缺口 2: 模块 B 没有实现“本地小模型 textual gradient”

- `研究思路--第二版.md` 里要求客户端调用本地轻量模型，例如 Qwen-1.5B，针对 `x_bad` 和 `x_real` 生成自然语言 critique。
- 当前 `adapters/critics/fedtextgrad_critic.py` 只是调用启发式模板函数。
- `algorithms/critics/contrastive_critic_core.py` 的核心逻辑是词频差分、长度差分和简单脱敏。
- `configs/methods/critics/fedtextgrad_qwen.yaml` 中也明确写了 `engine: heuristic`。
- `models/backends.py` 中真正的 `TransformersTextBackend` 仍然是占位实现，运行时会直接报错。

因此，当前平台没有真正实现“本地小模型 textual gradient”，只是用启发式规则模拟了这一接口。

#### 缺口 3: 模块 C 只实现了最简化 UID 近似，DBSCAN-Attn 和 TSGD-M 未落地

- `adapters/aggregators/uid.py` 和 `algorithms/aggregators/summarization_core.py` 的行为是字符串归一化后按频次和信息密度排序。
- 这只是一个简化版规则压缩器，不是你设计里“服务端大模型做语义级 UID 总结”的完整实现。
- `adapters/aggregators/dbscan_attn.py` 与 `dbscan_attn_tsgdm.py` 都还是占位，运行时直接抛异常。

因此，服务端聚合与 prompt 迭代部分目前只实现了非常弱的近似版本。

#### 缺口 4: 模块 A 仅部分实现，而且是代理算法，不是完整算法

- `DataInf` 当前是 embedding 向量上的轻量 HVP proxy。
- `GRADMM` 当前是 embedding 均值距离 + cosine distance + rarity proxy。
- `IRA` 完全未启用，`adapters/scorers/ira_scorer.py` 直接抛出 `RuntimeError`。

这意味着模块 A 并没有按你的研究思路完整落地为:

- DataInf utility-driven diagnostics
- GRADMM penultimate-gradient mismatch
- IRA instruction-response alignment

当前更像“接口已设计，算法做了 MVP 近似或保留占位”。

#### 缺口 5: 数据流默认被压平成纯 text，削弱了 instruction-response 对齐实验

- `core/schemas.py` 中虽然保留了 `instruction`, `response`, `label` 字段。
- 但 `data/loaders.py` 默认会把 JSON 扁平化成纯文本，只填 `Sample.text`。
- 这会削弱 IRA、label-aware retrieval、instruction-response 对齐等实验路径。

#### 缺口 6: 默认客户端划分不是真正的 Non-IID 构造

- `data/partition.py` 目前是随机打乱后 round-robin 分桶。
- 这只能得到稳定随机切分，不能自然模拟研究思路中强调的机构差异、风格差异、领域差异型 Non-IID。

#### 缺口 7: 评价指标过轻，无法支撑“效用提升”类结论

- `evaluation/metrics.py` 只统计生成数、长度、多样性、critique 数、时延、上传 token、prompt token。
- 没有针对下游任务性能、坏样本识别质量、prompt 更新有效性、对齐收益等关键指标做评估。

## 3. 数值验证设计

### 3.1 验证目标

本次数值验证专门针对最关键的静态结论:

> 当前平台中，prompt 虽然会被写回系统状态，但并不会真正改变生成器输出。

### 3.2 验证方法

新增两份对照配置:

- `thesis_platform/configs/experiments/validation/validation_prompt_sensitivity_a.yaml`
- `thesis_platform/configs/experiments/validation/validation_prompt_sensitivity_b.yaml`

二者唯一实质差异是 `generator.initial_prompt`:

- A: `Generate formal congressional policy text with legislative and fiscal detail.`
- B: `Write casual travel diary snippets about beaches, coffee, and holiday moods.`

其余关键信息完全一致:

- scorer: `datainf`
- retriever: `knn`
- critic: `fedtextgrad_qwen`（实际为 heuristic）
- aggregator: `uid`
- dataset: `datasets/congressional_train.json`
- public seed: `datasets/initial_set.json`
- `seed = 123`
- `generated_per_round = 12`
- `num_clients = 3`
- `top_k_bad = 3`
- `rounds = 1`

执行命令:

```bash
python -m thesis_platform.scripts.run_experiment --config thesis_platform/configs/experiments/validation/validation_prompt_sensitivity_a.yaml
python -m thesis_platform.scripts.run_experiment --config thesis_platform/configs/experiments/validation/validation_prompt_sensitivity_b.yaml
```

输出目录:

- `outputs/thesis_platform/validation_prompt_sensitivity_a/`
- `outputs/thesis_platform/validation_prompt_sensitivity_b/`

## 4. 数值验证结果

### 4.1 运行时环境事实

本次实验运行日志显示:

- 公共 seed 样本加载数: `87,317`
- 私有训练样本加载数: `664,957`
- 客户端数: `3`
- 每客户端最大样本数: `6`
- 实际 embedder backend: `HashingEmbedder`

最后一项非常重要。虽然配置里给的是 `models/all-MiniLM-L6-v2`，但实际没有启用真实 SentenceTransformer，而是退回到了哈希嵌入。补查结果显示原因是当前环境缺少 `sentence_transformers` 包。

因此，本次实验是“当前真实可运行环境下的平台数值行为”，不是“理想 MiniLM 环境下的数值行为”。

### 4.2 A/B 对照结果

对 `round_000` 的核心产物做逐项比较，结果如下:

| 对比项 | 结果 |
| --- | --- |
| `generated_samples.text` 是否完全一致 | 是，`12/12` 完全一致 |
| `scored_samples` 中 `sample_id/client_id/score` 是否一致 | 是 |
| `selected_bad_samples` 的样本序列是否一致 | 是 |
| `client_critiques.text` 是否一致 | 是 |
| `prompt_update.rules` 是否一致 | 是 |
| `round_metrics` 是否一致 | 除时延和 `prompt_length_tokens` 外，其余一致 |

第一条生成样本在两组实验中的文本完全相同:

```text
hats this winter, whether you're feeling with a big floppy chic a cloche hat or looking with little bit
```

这说明在相同 seed 和相同 seed pool 下，只改 `initial_prompt` 并不会改变本轮生成文本本身。

### 4.4 聚合规则结果

两组实验生成出的 `prompt_update.rules` 完全一致:

1. `<ENTITY> more concrete detail and domain-specific structure to match the retrieved real examples.`
2. `<ENTITY> off-topic or overly generic wording that does not align with the real samples, such as: trends, digital, marketers.`
3. `<ENTITY> important domain terms and concepts that appear in real samples, such as: billion.`
4. `<ENTITY> off-topic or overly generic wording that does not align with the real samples, such as: surge.`

这进一步说明:

- critique 是由 bad/real pair 的词面差分驱动，而不是由初始 prompt 驱动；
- 服务端聚合本质上只是对启发式规则做压缩；
- 当前主链的“语义控制量”主要来自样本差异，而不是来自 prompt。

## 5. 数值验证解释

本次数值验证对静态代码复核提供了直接支持。

### 5.1 被验证成立的结论

#### 结论 A: Prompt 没有真正进入生成器

因为 A/B 两组只改了 `initial_prompt`，其余完全相同，但:

- `generated_samples.text` 完全一致，
- `scored_samples` 完全一致，
- `selected_bad_samples` 完全一致，
- `client_critiques` 完全一致，
- `prompt_update.rules` 完全一致。

所以可以确认，当前平台里的 prompt 变化不会传导到生成样本分布。

#### 结论 B: 当前 critique 与聚合链路是可运行的，但语义能力较弱

平台确实能稳定生成 critique 并聚合成 prompt update，这证明工程链路是通的。

但从 A/B 对照看，critique 与聚合输出几乎完全由样本词面差异决定，符合“启发式规则链路”的特征，不符合“本地小模型 textual gradient + 服务端语义摘要”的设计目标。

#### 结论 C: 当前实验环境下并未启用真实 MiniLM 嵌入

日志明确显示运行时用的是 `HashingEmbedder`，原因是缺少 `sentence_transformers`。

这意味着:

- 当前实验结果只能证明“平台在当前环境下可运行且行为如上”；
- 不能据此声称已经验证了真实 MiniLM/DataInf 语义空间下的效果。

## 6. 最终结论

综合静态代码复核和本次数值验证，可以给出明确判断:

> 当前 `thesis_platform` 还没有完整实现 `研究思路--第二版.md` 中设计的创新算法全部内容。

更精确地说:

- 工程主链已经搭起来了，可以稳定跑通一轮联邦式实验。
- 但关键创新点仍是“接口层存在、算法层近似或占位”的状态。
- 数值对照已经直接证明: 当前 prompt 更新不会真实改变生成器输出。
- 运行环境还暴露出一个额外问题: 嵌入模型静默回退到了 `HashingEmbedder`，当前实验并未启用真实 SentenceTransformer。

因此，当前平台更适合被定义为:

> “面向你所设计创新算法的 MVP 实验骨架与近似验证平台”

而不是:

> “已经完整实现你设计创新算法全部内容的正式实验平台”

## 7. 后续最优先补齐项

如果目标是让平台真正符合你的研究思路，优先级建议如下:

1. 先把 generator 改成真正消费 `prompt_text` 的生成器，否则闭环的核心因果链不成立。
2. 接着把本地 critique 从 heuristic 替换为可运行的小模型 backend，例如 Qwen 系列本地推理。
3. 再补全 `IRA`、`DBSCAN-Attn`、`TSGD-M`，把模块 A 和模块 C 从占位/近似升级成正式实现。
4. 修复 embedding 运行环境，确保不再静默回退到 `HashingEmbedder`。
5. 最后补下游任务收益、坏样本识别精度、prompt 更新有效性等评价指标。
