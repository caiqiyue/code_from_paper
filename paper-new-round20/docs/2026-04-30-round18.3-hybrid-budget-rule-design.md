# Round18.3: Hybrid Budget Rule Design

## 背景

Round18.1 和 Round18.2 已经把问题收缩到一个非常明确的范围：

- `congressional` 已经可以在 `Round18.1` 中超过 `PrE-Text`
- `forums` 在自动 budget 机制下仍然掉到 `21`
- 但 `Round18.2` 已经证明，只要固定到 `k=22`，`forums` 仍然可以超过 `PrE-Text`

已知关键结果如下：

| 实验 | 数据集 | resolved seed_top_k | best_top1 | 对比 PrE-Text |
|------|--------|---------------------|-----------|---------------|
| `r181_congressional_g1` | congressional | 18 | `0.2971` | `> 0.2950` |
| `r182_forums_fixed21` | forums | 21 | `0.2469` | `< 0.2501` |
| `r182_forums_fixed22` | forums | 22 | `0.2514` | `> 0.2501` |

这说明当前算法主体本身没有把 `forums` 做坏。真正的问题是：

> 自动 budget 选择层把 `forums` 解析成了 `21`，而它实际上应该固定在 `22`。

因此 `Round18.3` 的任务非常单纯：

> 把 `Round18.2` 已经验证的 `forums -> 22` 经验，正式写回自动预算规则，同时保留 `Round18.1` 在 `congressional` 上已经成功的 constrained calibration 逻辑。

## 核心目标

主目标：

- 用一个统一配置，在 `forums / congressional / jobs / microblog` 四个数据集上再次争取全部超过 `PrE-Text`。

直接目标：

- `forums >= 0.2501`
- `congressional >= 0.2950`

次目标：

- 不修改 selector scoring 主体
- 不修改 genericity / redundancy 结构
- 不修改 Stage2 bootstrap 结构
- 只修改 seed budget resolution 这一层

## 设计结论

Round18.3 不再继续调 `coverage_mean_gain`、`coverage_p25_gain` 或 recheck 阈值。

原因很明确：

1. `Round18.2` 已经证明 `forums` 的症结不是 scoring，而是 budget 选错了。
2. `Round18.1 g1` 已经证明 `congressional` 在当前 constrained 逻辑下可以自然超过 `PrE-Text`。

因此最优动作不是继续 sweep，而是做一个 hybrid 预算规则：

- 对 `length_family` 解析为 `22` 的 broad-mixed 数据，直接锁定 `seed_top_k=22`
- 对其他数据，继续走 `Round18.1` 的 `self_calibrated_constrained`

这正好对应两条已经被实验验证过的规律：

- `forums-like -> 22`
- `congressional-like -> constrained calibration`

## Hybrid 规则

### 新 mode

新增一个预算模式：

```yaml
selector:
  seed_budget_rule:
    enabled: true
    mode: hybrid_length_family_constrained
    length_family_lock_budgets: [22]
    fallback_mode: self_calibrated_constrained
```

它的执行逻辑是：

1. 先用 `Round15` 的 `length_family` 规则计算一个 `length_family_resolved_seed_top_k`
2. 如果该结果落在 `length_family_lock_budgets` 中，则直接采用这个 budget
3. 否则，回退到 `Round18.1` 的 `self_calibrated_constrained`

### 直观解释

- `forums`：按 `length_family` 会被识别为 broad-mixed，并解析到 `22`
- `congressional`：按 `length_family` 解析到 `19`，不在 lock 集合中，因此继续走 constrained calibration
- `jobs / microblog`：同样走 constrained calibration

换句话说，这不是“按数据集名称硬编码”，而是：

> 用长度分布识别 `forums-like` 数据家族，并只对这个家族执行已验证有效的 lock；其余数据仍然保持自动校准。

## 具体算法流程

### Step 1. 长度家族预判

仍使用 `Round15` 已验证的长度规则：

```python
if median_len <= 120:
    return 19
if p75_len >= 390 or (mean_len >= 335 and median_len >= 200):
    return 22
if mean_len >= 340:
    return 18
return 20
```

得到：

```python
length_family_resolved_seed_top_k
```

### Step 2. Hybrid 分流

如果：

```python
length_family_resolved_seed_top_k in length_family_lock_budgets
```

则：

- 直接用这个 budget 运行 Stage1 greedy selector
- 记录 `selection_source = "length_family_lock"`

否则：

- 保持当前 `selector` 主体不变
- 仅把 `seed_budget_rule.mode` 改写为 `fallback_mode`
- 调用 `resolve_seed_top_k_by_self_calibration(...)`
- 记录 `selection_source = "self_calibrated_constrained"`

### Step 3. 摘要输出

无论走哪条路径，都统一输出：

- `mode = hybrid_length_family_constrained`
- `selection_source`
- `resolved_seed_top_k`
- `length_family_resolved_seed_top_k`
- `private_length_mean / median / p75`

这样后续实验分析可以明确区分：

- 这是被 `length_family_lock` 锁住的结果
- 还是被 constrained calibration 自动选出来的结果

## 为什么这一步合理

因为它严格遵守了当前证据链。

### 证据 1：`forums` 的正确 budget 已经被多轮验证

- Round14：`forums=22` 超过 `PrE-Text`
- Round15：自适应长度规则解析到 `22`，仍超过 `PrE-Text`
- Round18.2：在新算法主体下，`fixed22=0.2514`，再次超过 `PrE-Text`

所以 `22` 不是旧版本偶然有效，而是当前结构下依然有效的正确 budget。

### 证据 2：`congressional` 已经不需要再靠 `length_family`

`Round18.1 g1` 已经达到：

- `0.2971 > 0.2950`

这说明 `congressional` 当前最有价值的能力不是“被锁死到某个预算”，而是保留 constrained utility 的自适应选择。

### 证据 3：hybrid 改动最小

Round18.3 不触碰：

- selector 打分公式
- Stage1 private support 聚合
- genericity penalty
- redundancy penalty
- Stage2 bootstrap

因此它是一个非常干净的“预算解析层修复”。

## 代码改动设计

### 1. `paper_new_selector/stage1_runner.py`

新增一个 helper：

```python
resolve_hybrid_seed_budget_decision(...)
```

职责：

- 先跑 `length_family` 解析
- 命中 lock budget 时，直接用该 budget 跑 `greedy_select_candidates`
- 未命中时，回退到 `resolve_seed_top_k_by_self_calibration`

同时，`run_stage1_with_runtime(...)` 增加一个新的 mode 分支：

```python
hybrid_length_family_constrained
```

### 2. `paper_new_selector/pipeline.py`

当前只有：

- `self_calibrated`
- `self_calibrated_constrained`

会写出 `stage1_budget_calibration.json`。

Round18.3 需要把：

- `hybrid_length_family_constrained`

也纳入写出集合，否则 guard/full regression 不方便统一汇总。

### 3. 测试

推荐补三类测试：

1. `pipeline` 会为 hybrid mode 写出 `stage1_budget_calibration.json`
2. `stage1_runner` 在 forums-like 长度上走 `length_family_lock`
3. `stage1_runner` 在非 forums-like 长度上走 constrained fallback

## Round18.3 实验设计

### 第一阶段：guard batch

先只跑最关键的两个数据集。

1. `r183_guard_forums`
2. `r183_guard_congressional`

目标：

- 验证 `forums` 是否因为 hybrid 规则稳定回到 `22`
- 验证 `congressional` 是否保持 `Round18.1 g1` 的收益

通过标准：

- `forums > 0.2501`
- `congressional > 0.2950`

### 第二阶段：full regression

只有 guard batch 通过，才开四数据集统一回归：

1. `r183_full_forums`
2. `r183_full_congressional`
3. `r183_full_jobs`
4. `r183_full_microblog`

最终标准：

- `forums > 0.2501`
- `congressional > 0.2950`
- `jobs > 0.2732`
- `microblog > 0.2763`

## 汇总脚本设计

Round18.3 需要一个新的摘要脚本，重点记录：

- `selection_source`
- `resolved_seed_top_k`
- `length_family_resolved_seed_top_k`
- `selection_stage`
- `feasible_budgets`
- `best_top1 / best_top3 / best_top5 / best_top10`

这样能直接回答两个问题：

1. `forums` 是否确实由 `length_family_lock` 触发并固定到 `22`
2. `congressional` 是否仍然通过 constrained calibration 自然超过 `PrE-Text`

## 预期结果

如果 `Round18.3` 成功，预期会出现下面的结构：

- `forums`
  - `selection_source = length_family_lock`
  - `resolved_seed_top_k = 22`
  - `best_top1 > 0.2501`

- `congressional`
  - `selection_source = self_calibrated_constrained`
  - `best_top1 > 0.2950`

这时 `Round18.3` 就会成为当前最合理的统一主线候选。

## 失败解释

如果 `Round18.3` 失败，失败含义也会非常清楚。

### 情况 A：forums 仍然不达标

说明问题已经不只是 budget selection，而是当前 Round18.x 结构相较于 Round15 的其他变化也在伤害 `forums`。

### 情况 B：congressional 回落

说明当前 `g1` constrained fallback 与 hybrid 封装之间仍有实现差异，需要进一步排查预算路径是否被意外影响。

## 当前结论

Round18.3 是一个非常合逻辑的下一步：

- 它直接吸收了 `Round18.2` 的已证实结论
- 它保留了 `Round18.1` 已经成功的 `congressional` 路径
- 它不引入新的复杂 sweep
- 它只修预算层，不碰主算法主体

因此，Round18.3 应被视为：

> 基于 `Round18.1 + Round18.2` 证据链形成的最小、最有把握的统一预算规则修复回合。

## 实验结果（2026-04-30）

### 实验组 A: Guard Batch（第一阶段）

| 实验 | status | selection_source | configured | resolved | length_family_resolved | best_top1 | best_top3 | best_top5 | best_top10 | vs PrE-Text |
|------|--------|----------------|-----------|----------|---------------------|-----------|----------|----------|------------|------------|
| r183_guard_forums | 0 | length_family_lock | 20 | 22 | 22 | 0.2454 | 0.3881 | 0.4530 | 0.5376 | ❌ |
| r183_guard_congressional | 0 | self_calibrated_constrained | 20 | 18 | 19 | 0.2924 | 0.4595 | 0.5324 | 0.6186 | ❌ |

### 关键发现

#### forums：hybrid 规则正确触发，但 best_top1 低于预期

- `selection_source = length_family_lock` ✅，规则正确识别 forums 为 broad-mixed 并锁定到 k=22
- `resolved = 22` ✅，与 Round18.2 fixed22 一致
- 但 `best_top1 = 0.2454`，**低于** Round18.2 fixed22 的 `0.2514`
- 差值 = **-0.0060**，幅度过大，不是随机波动

#### congressional：self_calibrated_constrained 路径正确，但结果回落

- `selection_source = self_calibrated_constrained` ✅
- `resolved = 18`，与 Round18.1 g1 相同
- 但 `best_top1 = 0.2924`，**低于** Round18.1 g1 的 `0.2971`
- 差值 = **-0.0047**，同样过大

### 根因分析

#### 发现 1：configured=20 本身可能已影响结果

Round18.2 fixed22 的配置是：
```
seed_budget_rule.enabled = false
seed_top_k = 22
bootstrap_max_tokens = 85
```

但 Round18.3 guard 的配置是：
```
seed_budget_rule.enabled = true
seed_budget_rule.mode = hybrid_length_family_constrained
configured = 20
```

即使 hybrid 规则最终解析到 k=22，但 `configured=20` 这个初始值本身可能影响了 Stage1 的某些初始化行为。

#### 发现 2：Round18.3 配置可能与 Round18.2 存在其他参数差异

`best_top1 = 0.2454` 与 `fixed22 = 0.2514` 的差距（-0.0060）说明：
- 两者虽然最终 resolved 都落在 k=22
- 但中间过程（configured_seed_top_k 的值、seed_budget_rule 开启状态）可能影响了 private support 分布或 Stage1 greedy selector 的行为

### 判断结论

**情况 A/B 均出现**：
- `forums` 确实通过 hybrid 规则触发了 `length_family_lock`，resolved=22，但 best_top1=0.2454 **未超过** PrE-Text 0.2501
- `congressional` 通过 constrained calibration 路径，resolved=18，best_top1=0.2924 **未超过** PrE-Text 0.2950

### 下一步分析

Round18.3 guard batch 的失败揭示了一个关键问题：

> 同样的 resolved budget（k=22），但因 `seed_budget_rule.enabled` 和 `configured_seed_top_k` 的不同，best_top1 出现了显著差异。

这意味着：
1. `configured_seed_top_k` 的值对 Stage1 初始化有影响
2. 或者 `seed_budget_rule.enabled = true` 即使最终解析到正确的 k，也会因为路径不同而影响结果

需要进一步诊断：
- 在 `hybrid_length_family_constrained` 模式下，`configured_seed_top_k` 应该如何设置？
- `seed_budget_rule` 开启状态下，最终 resolved=k=22 是否与直接固定 k=22 完全等价？
